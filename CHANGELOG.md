# История изменений AWG Cascade Multi

## Unreleased — исправления аудита v2.5.2 (14 сентября 2026)

Базовая версия: `c1075240f3f94220160771af4eeddf81830d177f` (`v2.5.2`).
Запись ведётся вместе с изменениями кода. Это неопубликованная разработка.
Развёртывание и результаты выделенного стенда описаны ниже отдельно;
они не означают публикацию релиза или выполнение всех возможных испытаний.

Область работ: F01–F21 аудита, безопасные переходы сетевой политики,
проверяемый результат операций, восстановление после частичного отказа,
защита конфигурации и секретов, диагностика и регрессионные проверки.

### Реализованные изменения

| Аудит | Изменение поведения и затронутые компоненты |
|---|---|
| F01 | `awg-cascade-cfg.sh` разбирает только разрешённые ключи, не исполняет config, применяет значения только после успешного разбора всего файла. Убраны fallback на source в setup/client3. `awg-cascade-permissions.sh` закрепляет config/state/peers и родительские каталоги за root, выделяет доступ бота к SSH и чтению клиентских конфигов. В setup/sync wildcard sudo заменён явным списком команд. |
| F02 | `awg-cascade-routing.py`: pin lookup приоритет 999 и отдельный per-source prohibit 1000. Защита сохраняется при исчезновении интерфейса и очистке таблицы. Watchdog сверяет фактическую маршрутизацию каждый цикл, не очищает таблицы 101–199 при старте, не кеширует неуспешное применение. |
| F03 | Сопоставление правил через JSON `ip -j rule`; сравнение полных селекторов и удаление только дубликатов с сохранением одного правила. Переводы строк больше не ломают определение существующего pin. |
| F04 | `awg-cascade-firewall.py` — общий backend для iptables/interclient/client3-fw. Отдельные управляемые цепочки, общий lock, предварительный restore --test, временные DROP выше jump-правил до завершения изменений. Ошибка оставляет защиту. Чужие правила сохраняются. IPv6 клиентов и бота блокируется явно. LAN-разрешения ограничены источником, получателем и интерфейсом назначения. |
| F05 | sync учитывает владельца и группу по умолчанию, права, неактивные таймеры и незавершённую активацию. `activation-pending` сохраняется при повторном sync; учтены Python backend-файлы. Добавлены `installed-version`, `active-version` и команда `awg-cascade-activate.sh`, которая проверяет зависимости, права, recovery, firewall, routing и сервисы до снятия pending. |
| F06 | exit-update возвращает ошибку при недоступном SSH, неполном комплекте, сбое WARP/ОС; не прячет ошибки apt за успешным echo. Сравнивает права файлов; обновляет stamp только при успехе. Временные upload-файлы уникальны для запуска. |
| F07 | install выбирает тег относительно обновлённого origin/HEAD, а не старого локального HEAD. Отказ при незакоммиченных исходниках, отсутствии release tag и неуспешном fast-forward. Неявного перехода на main при отсутствии тега больше нет. |
| F08 | `awg-cascade-awg3.py` заменяет односторонние правки: подготовка обоих узлов, root-only журналы, применение, проверка передачи данных и нового handshake, commit/rollback. Неудачный rollback сохраняет pending для повторного восстановления. Ключ header protection не выводится в лог. |
| F09 | Ошибка записи reservation становится ошибкой команды. Пустой токен не обходит чужую бронь. Незавершённый provisioning закрепляет индекс через долговечную запись; ключи и индекс повторно используются при повторе с тем же IP/именем. Сбой генерации ключей освобождает ещё не использованную бронь. |
| F10 | Единый `awg-cascade-provision.py` для бота и CLI. Сериализация provisioning на RU и на exit, уникальный root-only каталог загрузки. Exit сохраняет план и результат по идентификатору RU-ключа; повтор не создаёт новый shared-интерфейс. При выборе подсети учитываются занятые сети RU и exit. |
| F11 | SSH host-key registry переносится в `ssh/known_hosts`. Парсер AsyncSSH учитывает маркеры CA/revoked и нестандартные порты. Обновления атомарны и защищены lock; ошибка сохранения пина прерывает операцию. Обеспечен перевод строки перед новым ключом. |
| F12 | Проверка доступа именно ключом бота: отключены SSH config/agent, задан IdentitiesOnly. Успешная аутентификация посторонним ключом больше не выдаётся за проверку ключа бота. |
| F13 | WARP on защищён DROP на время перестройки; отдельный terminal prohibit предотвращает fallback при исчезновении warp0. Проверяются маршрут, правило и ответ Cloudflare `warp=on/plus`. Ошибка не публикует успешный результат. Изменения общего warp0 сериализованы, restore имеет общий бюджет ожидания. |
| F14 | `awg-cascade-transaction.py` сериализует peer add/remove/rotate, exit add/remove, client3. Сохраняет файлы, runtime и enabled-состояние интерфейсов до мутации. Ошибка восстанавливает снимок; прерванная операция восстанавливается следующей командой/boot recovery. Pin/LAN-изменения через data broker имеют отдельный журнал и синхронное применение политики. |
| F15 | `awg-cascade-backup.py` снимает согласованный снимок под блокировками, сжимает после их освобождения. Проверяет соответствие приватных/публичных ключей, PSK, адресов и AllowedIPs. В архив включён manifest с результатом проверки и SHA-256 файлов. Новый архив публикуется атомарно; ошибочный снимок не вытесняет предыдущие бэкапы. |
| F16 | Бот ожидает root data broker асинхронно вместо блокирующего flock. Таймаут/cancellation локальной команды останавливает группу процессов. Watchdog получает результаты из ограниченного пула probe-задач, не опрашивает все exit последовательно; не более одного reconnect за цикл. |
| F17 | Установщики больше не убивают apt/dpkg и не останавливают выполняющиеся package services. Приостанавливаются только ранее активные таймеры, с восстановлением при обычном завершении и обработанных сигналах. Проверяются configure/audit/check; сбой upgrade не объявляется успешной установкой. |
| F18 | SSH hardening сохраняет основной конфиг и drop-in каталог до изменений. При сбое validation/reload восстанавливает все изменённые файлы. Успех требует sshd -t, ожидаемых эффективных значений и успешного reload. |
| F19 | Provisioning env с PSK передаётся JSON через SSH stdin; удалены секреты из SSH argv. Изолированные временные каталоги, umask 077, удаление завершённого pending. AWG3 передаёт данные через stdin и не печатает префикс ключа. |
| F20 | Проверяется установленный файл модуля и статус DKMS для всех загрузочных ядер. `awg-cascade-reboot.py` дополнительно определяет фактический первый GRUB target; нестандартный выбор требует ручной проверки. Плановый reboot запрещён при незавершённых изменениях и на shared-exit без ручной координации. |
| F21 | Удалены автоматические reboot из setup/bootstrap. Старый unattended reboot заменён явной настройкой окна и отдельным проверяющим timer/service; прежнее AUTO_REBOOT=1 не активирует новый механизм без выбора окна. На exit установщик явно выключает unattended reboot. |

### Дополнительные исправления и функционал

- Закрыт отдельный обход в `awg-cascade-alert.sh --clear`: имя проверяется до удаления файла; запрещены пути и выход за каталог cooldown. Проверяется числовой cooldown.
- Новый `awg-cascade-doctor.sh` выдаёт JSON без ключей: схемы данных, права, pending, pin guards, firewall hooks и watchdog; ненулевой код при провале проверки.
- `BOT_ENABLED=0` позволяет установить и испытывать VPN без Telegram/ntfy. Сервис бота использует ExecCondition; настройка сохраняется в config.
- Venv создаётся заново системным Python под root; старый bot-owned venv не исполняется от root. Старый каталог сохраняется для диагностики. Предусмотрены права чтения/исполнения библиотек ботом.
- CLI-совместимые `.sh` entry points сохранены для новых Python backend. Python backend используют стандартную библиотеку, кроме существующих зависимостей самого бота.
- LAN UI сообщает о неуспешном применении правил. `sudo -n` исключает ожидание пароля у фоновой команды.
- `.gitattributes` фиксирует LF для shell/Python/systemd. CI дополнен регрессиями и компиляцией backend-файлов, сохранены проверки повторяющихся блоков и admin_only.
- Обновлена selftest-проверка управляемых firewall/NAT-цепочек и pending activation.

### Совместимость и операции восстановления

1. Перед обновлением сохранить проверенный резервный архив и рабочий SSH-сеанс.
2. Root-owned данные больше нельзя редактировать от awgbot напрямую. Изменения метаданных бота проходят через data broker; смена ключей и состава — через транзакционные helper.
3. `version` — совместимый stamp файлов; `installed-version` и `active-version` различают установку и применение. Повторный sync не означает активацию. Применение: `sudo /usr/local/sbin/awg-cascade-activate.sh`.
4. Локальная незавершённая операция: `sudo /usr/local/sbin/awg-cascade-recover.sh`. Если восстановление не удалось, журнал остаётся в `/var/lib/awg-cascade`; новые мутации должны остановиться.
5. Незавершённый AWG3: `sudo /usr/local/sbin/awg-cascade-awg3.sh awgN recover`; нужен исправный SSH к тому же exit.
6. Незавершённое добавление exit: повторить с тем же IP и именем. Не удалять `.provision-*.json` вручную: там ключи, индекс, стадия и данные уже созданного удалённого интерфейса.
7. При firewall error временный DROP остаётся намеренно. Исправить причину, повторить iptables helper, затем проверить doctor. Автоматическое удаление защиты ради доступности не выполняется.
8. Bot egress при пустом каскаде блокируется вместе с клиентским. Для аварийного управления нужен SSH; emergency ntfy использует основной интерфейс, если настроен.
9. Старое AUTO_REBOOT=1 требует повторного явного выбора окна. Shared-exit перезагружается вручную после согласования со всеми RU.

### Подтверждённые проверки на текущем этапе

- Linux Ubuntu 24.04 на предоставленном RU-стенде: `bash -n`, ShellCheck уровня error, Python compilation, `.github/check-duplication.py` — успешно.
- 8 регрессий `test_stability.py` — успешно: валидация, отказ atomic replace, LAN/IPv6 renderer и реальные iproute2/iptables в отдельном network namespace, включая исчезновение pinned-интерфейса и порядок временных guards.
- 4 регрессии `test_bot_stability.py` — успешно: конкурентные обновления без блокировки event loop, остановка process group по timeout, revoked/nonstandard-port host keys, ошибка сохранения TOFU и отсутствие финального LF.
- Полная установка и двухузловые испытания ещё выполняются. Эта запись не утверждает, что WARP, обновление, reboot и все fault-injection сценарии уже прошли стенд.

Учётные данные SSH, временные приватные ключи стенда и конфиги с секретами в репозиторий и эту историю не включаются.

## Продолжение Unreleased — интеграция и стенд (15 сентября 2026)

### Дополнительные изменения после первой серии проверок

- `routing.py` учитывает фактический JSON iproute2: `uid_start`/`uid_end` и отдельный `dstlen`. Исправлена ошибка повторной активации; добавлены регрессии повторного создания правил и отсутствия дубликатов.
- `transaction.py`: обработчик сигнала использует отдельное исключение `MutationInterrupted`. `InterruptedError` поглощался `selectors` как повторяемый EINTR, поэтому SIGTERM не прерывал операцию. Добавлена автоматическая регрессия ожидания subprocess.
- Дочерний helper наследует дескрипторы блокировок и запускается через независимый `timeout 120` с принудительной остановкой через 5 секунд. После SIGKILL родителя recovery ждёт завершения дочерней записи; откат не конкурирует с осиротевшим helper. При откате создания интерфейса снимается также его systemd enable.
- Таймауты peer add/remove/rotate и exit remove в боте увеличены до 300 секунд, provisioning — до 3300 секунд, чтобы внешний таймаут не обрывал внутреннюю транзакцию до её восстановления.
- Watchdog и бот зависят от recovery-service. Setup включает recovery; ошибка восстановления препятствует обычному запуску зависимых сервисов.
- Setup загружает безопасный парсер до повторного использования AWG-параметров. `installed-version`/`active-version` записываются после проверки сервисов, маршрутизации и firewall.
- Активация заранее оставляет pending. При ошибке после замены venv возвращается прежний каталог зависимостей; новый неудачный каталог сохраняется для диагностики. Pending остаётся до успешного повторного применения.
- Backup, reboot и doctor учитывают журнал изменения pin/LAN. Broker проверяет тип и уникальность списка LAN, существование выбранных exit и LAN-получателей при изменении политики. Правка заметки не требует применения сетевой политики.
- Watchdog не публикует успешный ECMP route при ошибке ядра; при отсутствии exit устанавливает blackhole default. Перестройка ECMP сериализована с мутациями; незавершённая транзакция также подавляет reconnect. Некорректный config останавливает запуск watchdog.
- WARP получает сохраняемый FORWARD kill-switch: трафик выбранного cascade-интерфейса не может выйти через интерфейс, отличный от warp0, даже при потере RPDB после reboot. Временный guard учитывается в status и снимается после проверки. Off снимает постоянную защиту для явно отключённого WARP.
- WARP install больше не маркирует трафик до on и не сбрасывает существующее desired state. Бесконечный `yes` заменён конечным вводом при регистрации wgcf, чтобы `pipefail` не принимал SIGPIPE за ошибку регистрации.
- WARP rekey сохраняет прежний config/account/profile в root-only журнале до удаления. Неуспешная операция восстанавливается следующей командой/restore; committed marker предотвращает откат во время удаления уже завершённого журнала. После rekey работающего WARP проверяется Cloudflare data plane.
- Sync учитывает ошибки удаления orphan, SSH hardening, reboot policy и daemon-reload; не требует active Telegram-сервис в режиме BOT_ENABLED=0.
- Exit-update различает штатное отсутствие файла/version stamp и ошибку SSH. Первый успешный deploy больше не остаётся ошибочным из-за отсутствовавших до установки файлов; проверка checksum не маскирует ошибку вычисления.
- Первый provisioning теперь доставляет также cfg, autoreboot и reboot.py. Комплект расширен в setup, sync, canonical provision и CI-проверке дублирования.
- Reboot guard повторно проверяет явное разрешение AUTO_REBOOT/REBOOT_POLICY при выполнении таймера и отказывается от непроверенного GRUB `next_entry`.
- Client3 status корректно работает с нулём пиров, не прерывая успешный up из-за кода grep. Down удаляет точное LAN-правило priority 997 и переприменяет routing.
- SSH `--check` включает `sshd -t` и проверку keyboard-interactive authentication. LF дополнительно закреплён для YAML и Markdown.

## Продолжение Unreleased — решение по F21 и правки после разбора (15 сентября 2026)

### Решение владельца по F21

Замечания F21 признаны полностью: ветка перезагрузки на RU не была fresh-only,
перезагрузка exit'а не смотрела на `shared_mode`, а возвращение подтверждалось
существованием каталога и handshake'ом младше 180 секунд — то есть старый,
снятый до перезагрузки, handshake проходил проверку.

Первоначальное исправление сняло автоматическую перезагрузку целиком. Это
возвращало ручной шаг «не забудьте перезагрузиться», от которого отказались
14 сентября по прямому требованию владельца, и аудит такого не требовал — в
нём сказано «явная политика reboot never / fresh-only / scheduled».

Принято решение: **fresh-only**. Автоматическая перезагрузка возвращена, но
разрешена только там, где доказано безопасна.

| Ограничение | Как реализовано |
|---|---|
| Только чистая нода | `AWGC_FRESH` снимается в начале установки, до того как она сама создаст version-stamp; повторный setup на действующей ноде не перезагружает её |
| Только проверенная цель загрузки | `awg-cascade-reboot.py` (F20): первая запись grub.cfg, статус `installed`, файл модуля для этого ядра; отказ при нестандартном GRUB_DEFAULT и одноразовом `next_entry` |
| Shared exit — никогда | провижининг считает `awg-in*.conf` на exit'е; при более чем одном интерфейсе перезагрузка пропускается |
| Возвращение — по смене `boot_id` | «SSH отвечает» больше не считается доказательством: отвечать может и не перезагрузившийся сервер |
| Туннель — по handshake'у новее момента перезагрузки | старый handshake больше не подтверждает восстановление |
| Отказ проверки не перезагружает | нода остаётся на старом ядре (чинится командой), а не загружается без модуля (чинится консолью хостера) |

Перезагрузка exit'а живёт в общем движке `awg-cascade-provision.py`, а не в CLI:
по требованию F21 бот и CLI используют одну реализацию жизненного цикла.
Неудача перезагрузки меняет результат операции — код возврата 2 при `ok:true` и
поле `reboot` в JSON. Это отличается от кода 1: exit настроен, добавлен и
работает, повторять провижининг нельзя. Оба вызывающих — CLI и бот — различают
эти исходы явно.

## v2.7.0 — ключ другой RU на существующий exit (15 сентября 2026)

Единственное место, где до сих пор нельзя было обойтись без ручной работы с
машины владельца. Exit после провижининга закрыт: вход по паролю выключает
ssh-harden, и зайти может только та RU, чей ключ уже лежит в authorized_keys.
Подключить работающий exit к НОВОЙ RU её же силами невозможно — у неё нет
доступа. Ключ должна положить RU, для которой этот exit уже свой.

Теперь это кнопка «🔑 Ключ другой RU» в карточке exit'а и helper
awg-cascade-exit-authkey.sh для CLI — одна реализация на оба пути.

Что проверяется перед записью:

- адрес берётся ИЗ state.json по интерфейсу или IP, а не из аргумента: иначе
  helper был бы универсальным «положи ключ на любой хост от root», а вызывает
  его бот, то есть сетевой ввод;
- строка должна начинаться с типа ключа — это отсекает опции
  (command=, from=, environment=), через которые в authorized_keys заезжает
  чужое поведение, а не просто доступ;
- ssh-keygen подтверждает, что это действительно ключ;
- во вводе ровно одна строка;
- запись идёт с гарантией перевода строки перед ключом, а результат
  проверяется ПО ОТПЕЧАТКУ: при склейке с соседней строкой grep ключ найдёт,
  а sshd — нет.

Ключ передаётся через stdin: он не секрет, но argv виден в ps всем на ноде.
Операция идемпотентна — повтор отвечает «уже был».

Проверено на живых нодах: свой ключ даёт added=false, мусор и строка с
command= отвергаются, неизвестный exit отвергается, а добавленный одноразовый
ключ реально пускает на exit (после проверки снят).

Удаления ключа тут нет. Когда RU выводят из эксплуатации, её ключ остаётся на
exit'ах — это стоит закрыть отдельно.

## v2.7.1 — вторая половина: RU отдаёт свой ключ в боте (15 сентября 2026)

В v2.7.0 появилась принимающая сторона — кнопка «🔑 Ключ другой RU» в карточке
exit'а. Отдающей стороны не было: публичный ключ новой RU можно было взять
только командой в терминале, то есть сценарий всё равно упирался в консоль.

Теперь ⚙️ Настройки → 🔑 SSH-ключ этой RU: ключ блоком для копирования,
отпечаток для сверки и короткая инструкция, куда его нести. В разделе
настроек, а не на экране Exits — вещь редкая, на виду ей делать нечего.

Полный сценарий без терминала:

1. Бот НОВОЙ RU: ⚙️ Настройки → 🔑 SSH-ключ этой RU → скопировать.
2. Бот РU, которой принадлежит нужный exit: 🌍 Exits → exit → 🔑 Ключ другой
   RU → вставить.
3. Бот новой RU: 🌍 Exits → ➕ Добавить exit.

Ключ публичный: доступа не даёт и существует ровно для того, чтобы его
отдавать. Приватная часть остаётся с правами 600 и в бот не попадает.

ВАЖНО для действующего каскада: принимающая сторона должна быть на v2.7.0 или
новее. RU на старых версиях этой кнопки не имеют, и для них шаг 2 по-прежнему
делается руками.

## v2.7.7 — остановка бота занимала полторы минуты (15 сентября 2026)

Замечено при подключении exit'а к переустановленной RU: `systemctl restart
awg-cascade-bot` держал вызвавший его скрипт 90 секунд, после чего systemd
добивал процесс по TimeoutStopSec.

Причина: между попытками переподключения бот спит до MAX_BACKOFF_SEC, а
обработчиков сигналов у него не было. aiogram ставит свои ТОЛЬКО на время
polling — но при обрыве связи мы из polling как раз и вышли, так что SIGTERM
уходил в пустоту.

Тем неприятнее, что бьёт это ровно там, где болит: на ноде без exit'ов, где
бот и так в постоянном backoff, а перезапускает его bootstrap-скрипт.

Теперь polling запускается с handle_signals=False, а сигналы обрабатываются
самим ботом — одинаково и в polling, и в паузе между попытками.

Замерено на живой ноде, условия воспроизведены подменой api.telegram.org в
/etc/hosts: было 90 с и добивание по таймауту, стало 1 с и «Deactivated
successfully». На здоровом боте рестарт тоже 1 с.

## v2.7.8 — A04 и A10 из аудита v2.7.6 (15 сентября 2026)

Оба замечания — о коде, добавленном в этот же день.

**A04. Провижининг терял возможность продолжения после поздней ошибки.**
Журнал операции удалялся ДО применения протокола, записи version-stamp и
перезагрузки exit'а. Сбой на любом из этих шагов оставлял exit уже в state,
но без журнала: повтор упирался в «exit already exists», а сообщение об
ошибке предлагало именно повтор. Инструкция по восстановлению вела в тупик.

Журнал теперь снимается последним действием, а повтор с тем же IP и именем
доигрывает оставшиеся шаги: наличие exit в state означает, что RU commit
прошёл и переделывать его нельзя.

**A10. После перезагрузки не проверялось фактически загруженное ядро.**
Строка «done: ядро X» повторяла ядро, намеченное ДО перезагрузки. Загрузчик
мог поднять другое — туннель на нём тоже работает, поэтому ни смена boot_id,
ни свежий handshake этого не показывали. Теперь `uname -r` сверяется с целью,
и расхождение даёт отказ, а не успех.

Проверено моделью с подменой внешних шагов: поздний сбой оставляет журнал и
повтор доигрывает операцию; при другом загруженном ядре возвращается
«failed: загрузилось ядро …, ожидалось …» вместо «done».

## v2.7.9 — A01 из аудита v2.7.6: гонка при исправлении прав (15 сентября 2026)

Замечание о правке v2.7.3 — то есть о коде, которым чинили другой дефект.

Каталог /etc/awg-cascade/ssh принадлежит боту, а root менял права
known_hosts `chown`-ом ПО ИМЕНИ. Между проверкой «это не symlink» и сменой
прав скомпрометированный бот успевает подставить на это имя ссылку — и root
меняет владельца произвольного файла в системе. Предварительная проверка
такую гонку не закрывает в принципе: между ней и следующей командой проходит
время.

Теперь файл открывается один раз с O_NOFOLLOW, а права меняются через
дескриптор (`fchown`/`fchmod`): подменять имя после открытия бессмысленно —
работа идёт с конкретным inode. Дополнительно отвергаются не-обычный файл и
жёсткие ссылки: через них можно подсунуть чужой inode, не создавая symlink.

Вариант «отобрать каталог у бота» рассмотрен и отклонён: бот переписывает
known_hosts через временный файл и os.replace, а это требует права на запись
в каталог — TOFU и «забыть ключ» сломались бы.

Проверено на живой ноде тремя случаями: файл с чужим владельцем приводится к
боту; подмена имени симлинком на root-овый файл отвергается по ELOOP и права
приманки остаются нетронутыми; отсутствие файла — штатный пропуск.

## v2.8.0 — A05 из аудита v2.7.6: перезагрузка exit'а из бота (15 сентября 2026)

Экран подтверждения считал совпадения версии ядра во всём выводе `dkms status`.
Совпасть могла строка другого модуля или состояние `built` — и владелец видел
«всё готово» там, где модуля для целевого ядра нет. После подтверждения шёл
прямой `systemctl reboot`, мимо guard'а, который в проекте уже есть.

Теперь готовность проверяет `awg-cascade-reboot.py` на самом exit'е: фактическая
первая запись grub.cfg, статус installed именно для amneziawg, наличие файла
модуля под это ядро, отказ при нестандартном GRUB_DEFAULT и одноразовом
next_entry. Проверка повторяется ещё раз прямо перед командой — между экраном и
нажатием состояние ноды могло измениться.

Ручное исключение отделено от проверенной перезагрузки, как и требовал аудит:
при отказе кнопка называется «⚠️ Перезагрузить без проверки» и ведёт на
отдельный обработчик, а факт такого ребута пишется в журнал бота.

Заодно экран предупреждает, если exit ОБЩИЙ: сейчас оба наших exit'а несут
туннели двух RU, и перезагрузка из одного бота роняет клиентов второй ноды,
про которых этот бот ничего не знает.

Проверено на живых exit'ах: при готовности — `guard_rc=0` и цель загрузки в
ответе; при подмене GRUB_DEFAULT на `saved` — отказ с причиной и переход на
кнопку ручного исключения.

## v2.8.1 — временное окно входа по паролю на exit (15 сентября 2026)

Развилка «новая RU не может подключить работающий exit» разомкнута со стороны
той RU, у которой доступ есть. Кнопка 🔓 Вход по паролю в карточке exit'а
открывает окно на 30 минут; провижининг с новой ноды проходит по паролю и сам
же выключает его обратно — ssh-harden отрабатывает в конце.

Это НЕ решает исходную проблему целиком: бот новой ноды всё равно нем, пока у
неё нет ни одного exit'а, и команду bootstrap по-прежнему надо дать в консоли.
Убирается ровно один шаг — чтение публичного ключа из терминала новой ноды.

Реализовано helper'ом на стороне RU, как и обмен ключами: одна реализация для
бота и CLI, на exit'ах доустанавливать нечего.

Две вещи, найденные проверкой, а не рассуждением:

- **Имя drop-in'а начинается с 00.** sshd читает sshd_config.d по алфавиту и
  берёт ПЕРВОЕ значение, а наш hardening пишет `no` и в 99-, и в 50-.
  Файл с именем 99- не сработал бы вовсе.
- **Persistent=true не переживает перезагрузку.** Так было заявлено в первой
  версии — и оказалось неверным: на живом exit'е просроченный OnCalendar не
  сработал, потому что stamp-файл создаётся уже при включении таймера, а
  догоняются только запуски, пропущенные ПОСЛЕ последнего записанного.
  Поэтому закрытий теперь два: таймер по сроку и тот же юнит в
  multi-user.target, то есть на загрузке. Перезагрузка внутри окна закрывает
  его досрочно — это осознанный размен: переоткрыть дешевле, чем однажды
  оставить пароль включённым и не заметить.

Ответ строится по фактическому `sshd -T`, а не по тому, что команда не упала.

Проверено на живом FI-1: окно открывается и подтверждается на самой ноде,
закрывается по таймеру (13:39:17, drop-in удалён, sshd -T = no), закрывается
имитацией загрузки, закрывается вручную; после цикла на exit'е не остаётся ни
drop-in'а, ни активных юнитов.
